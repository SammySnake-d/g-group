## 定性与代码依据

`packages/server/proof/g6/contracts.ts:103–110` 的历史 K5 从 `inboundLines(c.request)` 读取呈现编号，随后直接比较 `hostDebt.refs.seq`，并以后来检查材料里的文本相同判断补查成功。`capture.ts:46–75` 不把编辑/撤回事件编号映射到其 target。

宿主 `captureSources` 则将非 `message` 事件映射到 `event.body.target`，再读取该消息当前 revision。固定提交中的位置分别为：

- g2 `4c9a372…`，`packages/server/src/host.ts:2206–2222`。
- g3 `122e0d4…`，`host.ts:2233–2249`。
- g4on `3218bc7…`，`host.ts:2253–2269`。

因此三个 E1 请求里呈现的 `#3` 是编辑事件；其冻结 `sources` 明确为 **消息 #1、revision 3**。新版本仍须检查或留欠账，不能因编辑而豁免。原判据却在台账里找来源消息 #3，造成误报。

g3 `host.ts:2251–2261` 的 `readCoverageMaterial` / `disposeCoverage` 会使旧版本失效，并为仍有效的当前版本建账；`memory-coverage.ts:77–87` 将失效工作保留为 `state=failed`、带 disposition、blocked 的记录，并未抹掉。`failCoverage` 在 `memoryCoverage.fail` 落账后才发出 `reflect-failed` 报告。`MemoryCoverage.begin` 在 g3 `memory-coverage.ts:37–43` 用以下身份公式：

```text
sha256(JSON.stringify([contactId, sorted({roomId,seq,revision}[]), sorted(inboxIds), sorted(unique(rooms))]))
```

本附件的四份都是单 DM、无 inbox。核对脚本按此公式重建 coverage ID，与原 `reflect-failed` 报告 ID 逐条核对；没有把重建值冒充原 call 中直接记录的字段。

## 必须保留的边界

- **不能宣告全部 K5 或 AC-42 通过。** 这只是四份固定记录中的四条误报定性；其他调用、题目、模型和合同没有在本附件接受验收。
- 原 `driver.ts:179–190` 采集 hostDebt 时丢掉 coverage ID、revision、disposition，只保存 `{roomId,seq,state}`；仅凭该投影无法区分旧 #1 与新 #1，也不能证明重试时间、处置原因和每个版本的最终状态。本次还依赖请求 sources、失败报告 ID 和固定源码路径。
- R1 call 12 的覆盖关联按固定 identity 公式重建；原 call 没直接带 coverage ID。脚本明确输出 derivedCoverageId，不掩盖这一采集缺口。
- 四份记录均有 `remember sourceSeq=3` 被宿主拒绝；最终记忆中也存在仍为 active 的旧内容。**本附件不把这些行为判成正常或已修复**，不以 K5 误报解释或覆盖它们。
- 不能通过跳过所有 edit/retract 输入来“修正”判据。E1 的新 #1/rev3 仍是有效检查义务；撤回事件、原文、canonical source 和 coverage work 必须区分。
