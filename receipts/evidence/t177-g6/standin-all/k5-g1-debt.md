# K5 在组②③④的判定复核:是 runner 判据问题,不是 G1 缺陷

结论:**判据问题**。G1 把失败的检查记成了欠账(覆盖台账里 state=failed、来源就是那条消息),没有静默清账;旧版 K5 要求「在这次运行内再被成功检查一次」,而补查的重试时机由宿主的重试策略(backoff)定,短运行里排到运行之后是正常的。K5 已改成:**之后成功检查过,或留下欠账记录(来源含这条)**,二者有一即守住。

## g2 · T1(题集原文:`以后提交代码前都先跑一遍单元测试`)

- 运行状态 `ok`,调用 10 次;注入的故障落在第 3 次调用(检查):`truncated`。
- 宿主自报欠账(原始记录 hostDebt):`{"A": {"counts": {"ok": 2, "failed": 1}, "refs": [{"roomId": "dm-c-mwc945cq-1", "seq": 1, "state": "failed"}]}}`
- 欠账来源(refs)里的 seq=1 就是那条消息(发出记录 sent 里 seq 1 = `以后提交代码前都先跑一遍单元测试`),state=`failed`。
- 之后成功的检查在第 [7, 10] 次调用,它们的材料里没有这条消息(消息已离开第 4 块),所以这次运行内没有再成功检查到它——这正是旧判据误报的原因。

## g2 · M1(题集原文:`以后开会都提前五分钟提醒我`)

- 运行状态 `ok`,调用 9 次;注入的故障落在第 3 次调用(检查):`parse_failure`。
- 宿主自报欠账(原始记录 hostDebt):`{"A": {"counts": {"ok": 2, "failed": 1}, "refs": [{"roomId": "dm-c-mwc945p9-1", "seq": 1, "state": "failed"}]}}`
- 欠账来源(refs)里的 seq=1 就是那条消息(发出记录 sent 里 seq 1 = `以后开会都提前五分钟提醒我`),state=`failed`。
- 之后成功的检查在第 [6, 9] 次调用,它们的材料里没有这条消息(消息已离开第 4 块),所以这次运行内没有再成功检查到它——这正是旧判据误报的原因。

## 组① 的对照

组①(基线 4efdee0)没有覆盖台账:`hostDebt` 为 null,失败的检查之后既没有再检查成功、也没有欠账记录 → K5 未守住(真缺陷,v0.2 缺陷 1)。

## 判据改动

- 旧:`之后必须有一次成功的检查覆盖同一条消息`,否则未守住。
- 新:`之后成功检查过` 或 `宿主把这条消息记成非 ok 的覆盖欠账(hostDebt.refs 含 roomId+seq)`;两者都没有才未守住;报告里写明「只要求欠账在、重试排上,不要求这次运行内补完」。
- driver 相应记录 `hostDebt = { counts, refs: [{roomId, seq, state}] }`(有 memoryCoverage 接口才读)。
