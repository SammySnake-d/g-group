`processMatch`（`procgroup.ts:95`）改按 PID + `ps lstart` 启动身份判断，进程组变化不再被当成退出；身份读不到返回 `unknown`，确认循环遇到 `unknown` 或读不到进程表就返回 `ok:false`（`stop-confirm.ts:37`、`:45`）。

独立验证用自写探针 `probe-r2.mjs`：真实 Python 父子进程，真实发 SIGKILL（不拦截 `process.kill`），判据是「`confirmStopped` 返回 `ok:true` 之后，登记过的夹具进程还有活着的」。

**红提交是真红。** `ed46e123` 相对 `e2815b6b` 只改了 `quiesce.test.ts`（+74/−1）。在 `ed46e123` 上单跑该文件：7 条，5 过 2 败，无 skip/todo/cancelled；失败的正是两条 CORR-001 用例，原因是业务断言——纯函数用例 `false !== true`「同一启动身份换组后仍是存活的原进程」，真实时序用例 `true !== false`「原进程仍可核对且存活时不能确认已停止」，不是加载失败或超时。`45976fca` 上同一文件 7/7。红绿之间测试文件的差异是两处类型写法（`as unknown as` 换成 `ProcRow`）和旧纯函数用例补了启动身份列与一条 PID 复用断言；后者在红提交上本来就是过的，不算先红。

**`lstart` 作为身份是否站得住。** macOS 上 PID 复用到同一秒内启动的概率可以忽略；担心的是 Linux 老版本 procps 的 `lstart` 会在两次 `ps` 之间差 1 秒。在 box4 对同一进程以 50 毫秒间隔采 3000 次，全部是同一个值；该版本没有这个问题。更老的 procps 没测。

## 必修：真实产品缺陷

### CORR-002 / High：停止确认期间新出生的同组子进程不再被关掉，仍返回已停止（本轮引入的回归）

位置：`packages/adapter-cc-compute/src/stop-confirm.ts:28–48`。

`known` 只在进入函数时由「停止前快照 + 一次 `treeNow(root)`」定下来，循环里不再重新找；旧实现循环里每轮都有的 `signalGroup(root, "SIGKILL")`（对 CLI 进程组整组发）在这次提交里被删掉了。于是从第 28 行那次读进程表，到第 48 行把派生它的进程杀掉之间（至少隔一次 `ps -A`，本机空闲时实测中位 16 毫秒），任何新 fork 出来的子进程都不在 `known` 里：它还在 CLI 的进程组里、还活着，函数却返回 `{ok:true,killed:N}`。旧实现靠整组 SIGKILL 把这些后来者一并关掉。

经生产入口复现（`probe-adapter-churn.mjs`：`createComputeAdapter` → `spawn` → `stop` → `quiesce`，假 CLI 外包一层，起一个留在 CLI 进程组里、按固定间隔派生同组子进程的中性负载；判据同上）：

| 派生间隔 | `e2815b6b` 旧实现 | `45976fca` 新头 | 新头 + 只加回那一行整组 SIGKILL |
| --- | --- | --- | --- |
| 15 毫秒 | 0/10 | **10/10**，每次留下 1–3 个活进程，`quiesce` 均返回 `ok:true` | 0/10 |
| 50 毫秒 | 0/10 | 3/10 | 未跑 |
| 200 毫秒 | 0/10 | 8/10 | 未跑 |

直接调用 `confirmStopped` 的同类探针：macOS 15 毫秒间隔旧 0/10、新 10/10；Linux box4 旧 0/10、新 10/10（共留下 21 个）；4 毫秒间隔旧 1/10、新 10/10（旧实现在极高频下也有残余窗口）；50 与 200 毫秒间隔两边都是 0/10。这些数字随负载的相位变，不是稳定概率；能确定的是：同一负载下旧头不留、新头留，把那一行加回去又不留。

后果与 CORR-001 同类：`Host.afterRound` 信任 `quiesce` 的成功结果，会提交已确认停止并归还槽位，而助手起的程序还在跑。现实里对应的是停止时正在跑构建、测试或 shell 循环的任务。本轮复现的是适配器的错误确认返回值，没有包成一次完整的真实模型 service 运行。

修复要求：返回 `ok:true` 之前，必须有一次新读到的进程表证明「快照里的进程、它们的后代、CLI 进程组的成员」都不在了；期间新发现的活进程要纳入并关掉。保留 PID 复用不误杀的保护。补回归：「停止时有一个留在 CLI 进程组里、持续派生子进程的负载」，在 `45976fca` 上先按业务断言变红。

同一探针还显示一个**两版都有、不是本轮回归**的缺口：快照里的子进程先 `setsid()` 再生孙进程，孙进程既不在快照里也不在 CLI 进程组里，旧实现 10/10 留下子孙两个，新头 10/10 仍留下孙进程。它的父子链在停止前并没有断，是否算在「全部找出来关掉」的保证范围内需要作者按需求 §8.1 第 16 条给出结论；按上面的修复要求（杀之前先找活着的已知进程的后代）可以一并解决。本轮不单独以它打回。
