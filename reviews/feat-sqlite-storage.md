## 合并前必须修复

### F-01：同进程测试不能验证跨进程单一提交点（AC-21 / R-05）

位置：`packages/adapter-sqlite/src/store.test.ts:108-126`，被测实现 `store.ts:52-63,97-109`。

现有测试在同一 Node 进程中通过 `onCasRead` 同步嵌套第二个连接。独立 R17 仅将 `commitDoc` 的 SQLite 事务替换成**进程内布尔锁**；这会挡住该同进程嵌套，却不能挡住另一个进程。R17 类型检查通过、原有 37/37 测试仍绿。

两个真实子进程在同一文件、同一文档、版本 0 上定点交错，实测：

- 原实现：A 成功 `{ok:true,ver:1}`；B 等待后得到 `{ok:false,reason:"version-conflict",currentVer:1}`；最终保留 A 的内容。
- R17：A 和 B **均返回成功、版本均为 1**，最终只剩 A 的内容，B 被静默覆盖；同一独立探针退出 1。
- 原实现另一个短超时场景：B 先抛 `database is locked`，审查探针在 A 提交后**主动重试**才得到版本冲突。这个重试是探针做的，不代表宿主已有重试策略。

**返修要求**：把真实多进程、同一旧版本竞争及结果/最终内容断言纳入仓库测试；对进程内假锁等单点错误实际注入，证明新测试会红，正常不同文档对照仍绿。明确 busy 的调用方处理边界；不要求在本切片中伪造尚不存在的上层重试。

### F-02：持久化撤回可被完全漏写而现有测试仍绿（AC-05 / R-05）

位置：`packages/adapter-sqlite/src/store.test.ts:18-28,162-179`；实现插入点 `store.ts:75-83`。领域包的内存撤回测试不能代替 SQLite 的撤回落盘测试。

独立 R14 仅在 `appendEvent` 算出撤回事件后、INSERT 前直接返回，既没有写撤回事件，也没有抛错。该变异 typecheck 和原套件仍为 37/37 绿。独立探针按同一原发言者追加消息和撤回，再关闭重开：原版有两条事件、撤回正文正确且链校验通过；R14 只剩第一条，探针按事件数失败。

**返修要求**：增加真实 SQLite 的撤回追加、旧事件不变、关闭重开、序号/链/撤回内容断言；将漏写撤回作为单点埋雷，证明该测试会红。正常实现已通过本轮探针，不把 R14 当成现有实现已丢数据。

### F-03：冲突和重放时其他对象是否保持不变没有被标定（AC-21 / AC-31③ 存储子判据 / R-05）

位置：`store.test.ts:89-105,129-160`。现有不同文档/不同动作测试与冲突/重放测试分开，未把另一个对象同时放在现场核对。

- R16 只在文档 A 发生版本冲突时错误覆盖其他文档的内容；原套件 37/37 绿。独立探针先建 A、B，再对 A 用旧版本提交：原版 B 保持 `{value:"B",ver:1}`，R16 将 B 改成“错误覆盖”，独立探针红。
- R15 只在重放已有动作 A 时错误删除其他动作；原套件 37/37 绿。独立探针先记录 A、B，再重放 A：原版仍有 A、B，R15 丢掉 B，独立探针红。

**返修要求**：补上述同时存在多个键的负路径前后快照，并让各自单点变异被对应测试杀死。R15/R16 是人为注入的错误，**不是**声称当前实现已经发生跨对象损坏。

### F-04：收据整项“通过”和第 7 栏的检测保证越过已验证范围

位置：`receipts/feat-sqlite-storage.json` 的 `acceptance` 与 `unverifiable`。

- **AC-05**（`docs/spec/验收文档-v0.1.md:105`）包含编辑、撤回、纠正均追加新事件及不改原记录。当前 PR 只有存储入口，宿主所有写入路径尚未接线，原测试还没有 F-02 的撤回落盘回归。应把整项改为“未测”，在原因中单列已实测的存储子判据；不要求本 PR 提前实现宿主。
- **AC-21**（同文档第 136 行）要求同一版本并发提交时后提交者收到冲突。存储写事务在本轮跨进程可工作，但忙超时会抛异常、最终调用方如何重试仍未验证，F-01 的进程级回归也缺失；应将整项标“未测”，单列已经验证的存储子判据，待接线与重试证据补齐再判整项。
- **第 7 栏关于 `DROP TRIGGER` 后“这种篡改只能事后被 loadLog 的 verify 报 brokenAt”不成立。** 本轮删掉 DELETE 触发器，再删除最后一条事件并关闭重开：剩余一条、`check={ok:true}`；删除全部事件同样返回 `ok:true`。另实测改正文并重算后续 hash 也返回 `ok:true`。单纯改正文而不重算则正确返回 `{ok:false,brokenAt:1}`。因此现有链只能检查**当前保留下来的链的自洽性**，没有外部可信头/长度锚不能识别尾部截断、整链删除或重算；应据实修正文案，不把本意见等同于要求本片实现密钥或外部锚。
- **R-05** 的“通过”最多覆盖已列的 13 个埋雷，不能据此声称本片每条判据已完成充分双侧标定；F-01～F-03 的存活项需要按上述要求补测、重跑并据实更新收据。
