## 1. 本源：验收要解决的到底是什么

依据分级沿用本源性分析：A 定律/定理，B 大样本实证，C 机制确证，D 假说（须标注）。

1. **“绿”不等于“符合目标”，这个缺口不能消除，只能显式化。** 测试只能说明“没采到反例”，是否符合用户目标最终是人的判断（acceptance-atlas 开篇；依据 C）。所以验收的产物是一张写明“验了什么、没验什么、谁签字”的收据，不是一句“已完成”。
2. **自己验自己不构成证据。** 生产者自检和被测代码共享同一套假设和盲区，它的通过只是调试信息（meta-development：P ≠ O；pstack 写审分离；依据 C）。所以写的人和审的人必须分开，并且用机械门禁强制，不靠自觉。
3. **规则没有执行者就会复发。** 今天群里的事故（话题乱飞、用户手发“继续”、主稿被并发覆盖、静默当成验收）都是“写了规则但没东西拦”（poteto 2500PR [36:57]；本群日志；依据 C）。所以每条规则旁要写由什么执行，只靠文档执行的单列成缺口。

由这三条推出第 2 节的全部规则。

## 3. 一条验收标准怎么写

### 3.1 必填字段

| 字段 | 写什么 | 缺了怎么办 |
|---|---|---|
| ID / 来源 | 标准 ID；主稿 U/US/C-US 编号；用户消息号；主稿版本 hash | 无来源不收 |
| 优先级与准入 | `P0 门禁` / `P1` / `待决（主稿 8.1 某项）` / `待验证（假设未实测）` | 待决项只写分支各自的验收（R-12） |
| 用户可观察结果 | 一句话，含可数或可比较的量 | 不含可观测量不收 |
| 对象与状态格 | 落在哪个实体、哪台状态机哪一格、守哪条不变量 I1–I5 | 定位不到说明是底座缺口，回主稿修 |
| 事件序列 | 前置状态 + 多步动作，不是单个动作 | |
| 必须 / 禁止 | 两边都写 | 缺“禁止”是单边标准，不收 |
| 观测点 | 状态表 / 落盘日志 / 接口响应 / 真实窗口快照（R-07） | 只看 UI 文字或 agent 自报不算 |
| 执行者 | 第 2 节的执行者取值之一 | “仅文档”进缺口清单 |
| 阳性埋雷 | 故意改坏实现，必须红，红因文字对 | 埋雷不红 → 检查无效 |
| 阴性对照 | 同一输入只改一个开关，必须绿 | 防“什么都报红” |
| 证据层 | D 确定性底座 / X 真实跨层闭环 / S 非确定性质量，按风险选，不强制三层齐全 | |
| 状态 | 通过 / 失败 / 未测 / 不适用（R-08）+ 证据工件路径 + 裁决人 | |

### 3.2 每项能力配一份 feature map

格式照 pstack `create-verification-skill/references/feature-map-example/create-note.md`：到达 → 驱动命令 → 预期可见结果 → Proof 工件（状态表快照、落盘记录、窗口 aria 快照或截图）→ Gotchas（例如“提示保存成功不算证明，要重新打开读回”）。feature map 是实现交付物的一部分，和代码同一个提交，不事后补。

## 8. 验收流程

### 8.1 一个切片怎么走

1. 写 feature map 和行为测试，跑一遍，留下“红”的记录（R-02）。
2. 写实现，测试变绿；跑空实现红基线和双侧标定（R-03、R-05）。
3. 提交固定 commit，进入 `T5 InReview`；由不同联系人审查，对照原始需求和 feature map 盲审（R-01）。
4. 合流，跑真实跨层闭环（X 层用例），产出 Proof 工件。
5. 出收据（8.3），交付进入 `T8a` 等用户确认（R-09）。

### 8.2 谁判什么

| 判定 | 谁 | 依据 |
|---|---|---|
| 确定性用例通过 | 脚本 | 退出码 + 工件 |
| 代码与切片审查 | 非作者的联系人 | R-01 |
| 非确定性质量 | 评测脚本 + 人工抽检 | R-14 |
| 体验是否可接受、能否发布 | 用户 | 收据 + 自己试用 |

### 8.3 收据（每次验收一份）

沿用 acceptance-atlas `GREEN-RECEIPT` 七栏，至少写：
1. 通过的条目 ID 和证据工件路径；
2. 双侧标定情况，哪些只是声明、没真注入；
3. 埋雷存活清单（改坏了却没红的）；
4. 未测条目和原因；
5. 仍然“仅文档”执行的规则；
6. 判据版本、对应主稿 hash、复评日期；
7. 一句人写的话：“我为什么相信这次绿，它可能被哪个检查骗过”，必须点到一个具体 ID。

收据固定列出四项机器验不了的内容：第 7 栏那句话的质量；体验类结论；需求本身有没有漏（结构源是否忠实于用户原话）；埋雷选得好不好。
