# Contact and Gateway

`packages/server` wires Contact lifecycle, configuration snapshots, speaking turns, provider discovery, and usage. `packages/adapter-pi-contact` implements contact speaking and provider request wiring. Select the speaking model independently from the Compute model and harness. A turn captures its config snapshot, so a later edit takes effect at the next eligible boundary.

Changes to wire routing or prompt caching need adapter tests. Changes to the snapshot and rollback path need server tests. Contact context and Block 1 admission belong to [Context and Memory](context-and-memory.md).

### Group follow-up

The contact finds open and owned tasks in the current context and can read the task's requirement, owner, state, and revision with `read_task`. `claim_task` and `release_task` carry the read revision and the contact's own room message. A contact that loses a claim receives the winner's name through the existing private round inbox. In a round proposing a claim on an existing task, `dispatch_compute` cannot also create a task from the same room's latest user message. Other source messages and claims of other existing items aren't blocked by this check.

Contact replies wake other room members from the durable message. The default runtime does not cap per-root wake count or restrict independent contact posts by text equality, sender rate, or three-sender sequence. Explicit `loopGuard` limits set by an embedding host still apply. A root stopped by the former default may accept a new wake after upgrade, and the same message and target still deduplicate. The retired `roomPostBudget: false` option is accepted for source compatibility and has no effect; old budget rows are left untouched and no longer read.

At reply commit, the host resolves visible `@name` tokens against unique peers in the current room and records their contact IDs in `mentions`. The prompt identifies the sender and the explicit recipients separately. Group replies to a quoted and addressed user message go to its named contacts, who follow the new request and use the quoted text as background. An explicit request for silence applies to that message and its follow-ups. Named contacts can respond, and repeating the same acknowledgement on that thread does not post a second copy. Observers still process shared context and can contribute new information in ordinary discussion.

Round assembly includes up to the 10 most recent `T8_Accepted` tasks owned by the contact alongside active non-terminal tasks—attaching `, 交付 #<deliveredSeq>` once delivered so quoted replies map deterministically back to `taskId`—so post-completion user feedback can still identify and reopen completed tasks. Prompt guidance and tool descriptions (`CONTACT_SYSTEM`, `CONTACT_TOOLS`, and `verdict`) document `read_task`/`claim_task`/`release_task` for unassigned tasks, tell contacts that `deliver` completes ordinary tasks without waiting for explicit `"通过"`, avoid confirmation-nagging wording when no `codeRepo` worktree integration is needed, and require `verdict(revise)` (never plain `reply` text rewrites) to reopen either `T8a_Delivered` or `T8_Accepted` back to `T3_Running` for Compute revision while keeping explicit `verdict(accept)` optional. When the prior Compute instance is not live in the current host's `computeRuns` (such as after a server restart), `computeResumable` returns `false` so rework spawns a fresh Compute with the prior result and rejection feedback handoff instead of attempting to resume an expired in-memory handle.

### Helper replies

The Pi runtime answers a committed user `@Helper` in a direct message or group. `HelperDesk` supplies that room's context and posts the generated text as a reply to the original message. Helper uses the configured default speaking model and the existing Pi text request path. It reads the current room's active announcements, rules, and tasks and does not receive action tools through this entry. Global and sidebar Helper threads use their existing note and history APIs.
