# 开发手册：g-group 的设计与开发范式

> 来源：用户从 g-group#1188 起对原型提过的全部修改意见，以及 Argon（#1248、#1338）、Astra（`reviews/20261105-Astra-IM本源与历史建议/`）的建议。
> 用途：做任何新功能之前先读一遍，做完按“怎么验”自查。每条都写了我们自己犯过的错，方便对照。
> 维护：新教训按同样格式追加，写明来源消息编号。Argon 的设计指南（T-57）出来后并进对应章节。

---

## 动手前的检查单（每个新功能都过一遍）

1. 这个功能里的核心概念，写过概念卡吗？“它是什么、不是什么、最容易被想窄的地方”都写了吗？（原则 1）
2. 它为谁服务、能读什么、负责什么，定下来了吗？位置和样子是从这三条推出来的吗？（原则 2）
3. 它属于谁：群和软件、联系人、Compute 的产物、插件，还是 Helper？（原则 3）
4. 用户会从哪几个地方进到这里？每个入口想干的事一样吗？不一样就要给不同的视图。（原则 7、8）
5. 它有几种状态？每种状态在一屏里的主位置在哪？不看文字能分清吗？（原则 13、20）
6. 每个入口点进去都有完整内容吗？有没有“只有入口、点进去是空的”？（原则 21）
7. 走查脚本能从用户真实入口一路点到结果吗？（原则 23、24）
8. 这个功能依据的讨论结论，写进需求文档、概念卡或本手册了吗？每条注明来源消息了吗？（原则 35）
9. 修 bug、做功能、调性能，走的是原则 37–39 的步骤吗？每一步要交的证据都在仓库或收据里吗？审查人不是作者、厂商不同吗？（原则 37–41）
10. 自己说过"我会做"的事、用户交办且接下的事，都进了联系人的承诺账本吗？承诺有没有被静默丢掉？报「完成」的有没有对应产物？（原则 45；逐条处置、对账补 1 次等是待审方案，不作为检查项）
11. 这个功能会调模型吗？固定前缀还是逐字稳定吗？账本、状态笔记、新消息这些会变的东西放在前缀之后了吗？（原则 46）
12. 一个联系人同时做几件事时，用户分得清自己在回哪件吗？补充有没有串到另一件？Compute 有没有直接在群里说话？（原则 47；短名标签是待审方案，不作为检查项）
13. 要用户拍板的事，先作为一条消息发出去了吗？选项挂在消息下方、最后是「✏️ 自己回答」吗？交付是不是一条普通的 @你 消息，没有另造验收组件？（原则 48、53、54）
14. 同一件事只有一个入口吗？低频的东西是不是不常驻、按需在分栏里打开？看详情用分栏，不遮挡聊天？（原则 49、50、51）
15. 消息在前、状态灰字挂在消息最下面吗？同一个人的消息该合并的合并、一个回合结束就拆开吗？同一高度的空位用起来了吗？（原则 55、56、57）
16. 这个能力从创建、查看、修改、删除、试跑、运行记录到和消息互相跳转，整个生命周期都做了吗？走查既有冻结的画面比对，也有不冻结的交互实测吗？（原则 52、58、59）
17. 投递带引用的消息时，引用链往上带了前几级吗？每一级都标了上面还有没有、整条链多深吗？已删或无权读的一级停住了吗？（原则 60）
18. 这个功能会长时间跑吗？一轮没有进展时，宿主会判失败吗？失败带原因类别、在画板上看得到吗？「harness 说在重试」有没有被当成进展？（原则 64）
19. 这个功能会显示「谁读了、谁在做、做完没有」吗？已读是宿主按位置算的吗？群里的联系人进了已读名单吗？有没有拿表情、模型的一句「收到」当已读，或者拿已读当办完、当已处理？（原则 66）
20. 这次工作建了哪些临时克隆、构建、node_modules、测试产物？做完这一步清掉了吗？测试代码建的临时目录跑完自己删了吗？派出去的任务 brief 里带上清盘规则了吗？（原则 67）
21. 创建或修改 automation 时,使用的是不排队的模型吗？model 字段对应的 profile 是 `ai-iisbo-2/` 或 `ai-iisbo/` 前缀的吗？（原则 69）
22. 这次改动碰到了 harness 调用吗？每一轮都把这一轮生效的模型传给 harness 了吗（重试、任务话题、插话恢复这些路径也算）？换模型是在同一会话里、轮与轮之间换的吗？有没有在一轮中途发 `set_model`，或检测到模型变了就杀进程另起新会话？（原则 70）

## 一、怎么想：先吃透概念，再动手

### 原则 1 · 先把概念想透，再开发
- **反例**：
  - 插件系统被做成了“外部来源的消息”一个入口（#1251）。
  - 群的共享清单被做成了 Argon 产出的表格（#1246）。
  - Compute 被写成“就是一个 session”，漏掉了 Super-agent 的扩展方向（#1284）。
  - 定时被当成插件，其实是联系人自己的能力（#1286）。
- **正确做法**：动手前给每个核心概念写一张卡，写三件事：
  - 它像哪个成熟产品的什么能力；
  - 它不是什么，最容易被想窄的地方在哪；
  - 原型里放哪、长什么样。

  卡片要对上需求文档编号（U / US / D / AC），先请用户确认再开发。
- **来源**：#1266、#1251、#1246、#1284、#1286
- **怎么验**：每个新页面都能指回一张已确认的概念卡。概念卡里写的“边界”在原型里找不到反例。

### 原则 2 · 先定本质，再推位置和样子；不能倒过来
- **反例**：
  - Helper 先被定成“侧边栏、不混入对话流”，再倒推它是什么。结果把“职责隔离”误解成了“视觉隔离”：它明明可以像 QQ bot 一样在聊天里被 @、在聊天里回答（#1353，纠正 Argon #1352 和概念卡 v2）。
  - v1 又把它做成了盖在聊天上的浮层（#1251）。
- **正确做法**：先回答三个问题：
  - 它为谁服务；
  - 它能读哪些内容；
  - 它负责什么。

  然后从“用户在哪里叫它”推出“它在哪里出现”。以 Helper 为例，在哪里叫，就在哪里答：
  - 在聊天里 @ 它，回复是聊天里的一条消息；
  - 在聊天窗口里打开面板，它读当前聊天；
  - 用 ⌘K 全局打开，上下文是空的。
- **来源**：#1353、#1340、#1278
- **怎么验**：设计说明里，“位置 / 样子”那一节的每一句，都能追溯到“服务对象 / 可读范围 / 职责”里的某一条。

### 原则 3 · 先分清能力归谁，再排布局
- **反例**：共享清单被放成某个助手发的工件（#1246）。定时被放进插件卡（#1286）。
- **正确做法**：先列一张归属表，再决定放在哪：
  - **群和软件的能力**：公告、清单、群文件、成员、关联。
  - **联系人的能力**：说话、判断、认领、承诺、定时、记忆。
  - **Compute 的产物**：代码、文档、截图、检查点。
  - **插件**：取数据、发出去、加面板。
  - **Helper**：操作软件本身。

  按归属决定入口：群能力放在群的常驻位置，联系人能力放在联系人的工作台。
- **来源**：#1246、#1286、#1251
- **怎么验**：把某个助手移出群，群的清单还在。没装任何插件，也能给联系人设定时。

### 原则 4 · 隔离指的是工具和上下文，不是界面
- **反例**：把“软件操作工具不进联系人上下文”理解成“Helper 不能出现在消息流里”（#1352 → #1353）。
- **正确做法**：
  - 隔离的是工具和上下文：操作软件的工具只给 Helper，联系人不会照着 Helper 的回复去操作软件。
  - 显示上，Helper 照样可以在消息流里。
  - 读别的聊天、代你发消息之前，先让你确认。
- **来源**：#1251、#1353、#1340
- **怎么验**：检查联系人的工具清单里没有软件操作工具。群里 @Helper 时，回复出现在群里。全局 Helper 不经确认读不到任何聊天。

### 原则 5 · 照 IM 的心智做，但先判断它在 agent 群里本质是什么
- **反例**：QQ 的能力只做了样子，没有想它对 agent 有什么用（#1235）。另一个方向的错，是把 QQ 的功能一股脑全搬过来。
- **正确做法**：按本源性分析，逐项写清一项 IM 能力在 agent 群里本质是什么。例如：
  - 群公告和精华消息，本质是要所有联系人都知道的规则，要放进它们的上下文；
  - 会话置顶只是你自己的导航，和规则无关（Astra）。

  结论落到对照表，每项写清要不要、归谁、放哪。
- **来源**：#1235、#1257、Astra 建议稿 §1–§2
- **怎么验**：《IM 能力本源对照表》里每一项都有“归属 / 位置 / 需求编号”。

### 原则 6 · 状态名要说实话
- **反例**：
  - 把“规则已放进上下文”叫成“已读”，像是它已经懂了、会遵守（Astra）。
  - 让清单的状态直接照搬 Compute：Compute 跑完，任务就自动“完成”了（#1247 的助手建议，Astra 纠正）。
- **正确做法**：
  - 规则分“已装配”和“有行为证据”；
  - 清单任务分待认领、进行中、待验收、已完成；
  - 执行结束不等于验收通过，执行者不能替验收者批准。
- **来源**：Astra 建议稿 §1、§3
- **怎么验**：Compute 结束后，任务停在“待验收”。把认领人移出群，任务回到“待认领”。

## 二、怎么排：落点、空间、入口

### 原则 7 · 落点不同，视角就不同；不要为省事让所有入口共用一个视图
- **反例**：
  - 从左侧联系人列表进去，点“设置”，弹出的是和群里点头像一模一样的资料卡（#1334 附图）。
  - 记忆、预设、职责都看不到（#1334）。
  - 定时如果只放在头像里，看一遍要点十几次（#1286）。
- **正确做法**：
  - 在聊天里点头像，是想认一下是谁、私信、@，给一张轻量**名片**；
  - 从联系人列表进去，是要管理它，用**整个主面板**展开工作台（概览 / 职责与预设 / 记忆 / 定时 / 设置）；
  - 同一份数据从不同入口进来，过滤范围也不同：
    - 群里只看本群的定时；
    - 联系人工作台看它的全部定时，每条标明属于哪个群；
    - 「进展 → 定时」看所有人的定时。
- **来源**：#1334、#1286、Argon #1338
- **怎么验**：给每个对象列出所有入口，各写一句“从这里进来想干什么”。目的不同，视图就必须不同。走查要覆盖“联系人列表 → 工作台 → 切换标签”。

### 原则 8 · 主面板用来管理，浮层只做轻量的事
- **反例**：设置、定时、记忆都塞进一个浮动资料卡，层层套娃（#1334）。
- **正确做法**：
  - 浮层只放名片、确认、快速选择这类一眼看完的东西；
  - 要编辑、要浏览很多条的内容，一律放主面板或并排分屏；
  - 在主面板里点“设置”，就地换标签，不弹窗。
- **来源**：#1334、Argon #1338
- **怎么验**：浮层里没有超过一屏的列表，也没有“编辑后保存”的表单。

### 原则 9 · 常用的能力常驻在眼前，低频的收进分组列表；不要一排图标藏在右上角
- **反例**：v3 把群功能做成右上角一排按钮（#1230）。点头像少了“查看对话细节”（#1235）。
- **正确做法**：
  - 照 QQ 的布局做群聊右侧常驻栏：公告、清单、成员、在做的事；
  - 低频的管理功能用 Claude Desktop 式的悬浮卡片列表，分好组、可折叠；
  - 每个入口都写清楚是什么（#1251）。
- **来源**：#1230、#1235、#1251
- **怎么验**：右上角的按钮不超过 4 个，每个都有文字说明。群的常用能力不用点任何按钮就看得到。

### 原则 10 · 操作要贴着它作用的对象
- **反例**：消息的悬停操作条出现在左上角，离右边的消息很远（#1251 附图）。
- **正确做法**：
  - 照 QQ 的做法，右键或悬停时，在消息旁边就地弹出表情条和菜单；
  - Compute 出错时，那一行原地变红，行尾跟一个“重试”（Norman 的就近映射）。
- **来源**：#1251、#1244
- **怎么验**：左右两侧的气泡分别测悬停、右键和键盘操作，菜单都出现在消息附近。

### 原则 11 · 输入框上方只放要你回答的东西
- **反例**：出错提示挤进了输入框上方的托盘，还带一个“先不管”按钮（#1244）。
- **正确做法**：
  - 托盘只放引用、待发文件、A/B/C 提问、验收这类要你答的东西；
  - 不阻塞你的错误不进托盘；
  - 没有意义的按钮直接删掉：不点“重试”，本来就等于先不管（Cooper 的“不要审讯用户”）。
- **来源**：#1244、Argon #1248
- **怎么验**：制造一次 Compute 失败，输入框上方不出现任何东西。

### 原则 12 · 好的产品是一个整体，要从全局排布局
- **反例**：做一块补一块，所以不知道会话关联、插件这些放在哪（#1194）。
- **正确做法**：先列出全部能力和它们的归属，再分区：
  - 左侧：导航和会话；
  - 中间：聊天；
  - 右侧：群能力，或对象详情；
  - 并排分屏：Compute 和 Helper 面板。

  新功能先找到它在这张图里的位置。
- **来源**：#1194、Astra H20
- **怎么验**：新功能的设计说明里写明它落在哪一区、为什么。

## 三、怎么看：层级、对比、状态

### 原则 13 · 不同状态要一眼分清，不靠读字
- **反例**：“做完了，等你验收”“最近做完”和普通提示，用的是同一种字号、颜色和行高，只差一个小圆点（#1334 附图）。#1095 时用户就说过，等待决策和正常消息没有区别，容易被略过。
- **正确做法**：每种状态至少有两个视觉特征和别的不同：形状或图标、颜色、字重、占位。依据是 Treisman 的前注意加工：颜色、形状、大小可以一眼挑出来，不用读。要你动手的最显眼，做完的退到背景里（视觉层级），做完的不再花一整行墨水（Tufte）。具体样式见概念卡第 13 张：
  - **运行中**：绿；
  - **等你**：黄 / 橙，带底色和主按钮；
  - **出错**：红，左边一道竖线，行尾“重试”；
  - **做完**：灰色对勾，折叠起来；
  - **系统提示**：居中的浅灰小字。
- **来源**：#1334、#1095、#1286
- **怎么验**：截一张去掉文字只留样式的对照图，能分出全部状态。色盲模拟下仍然分得清（不只靠颜色）。

### 原则 14 · “看绿”：正常就安静，异常才抢眼；数据多也要有序
- **反例**：定时任务一条条平铺，几十条全是同一个重量（#1286 指出的风险）。
- **正确做法**：
  - 正常的只显示一行灰字；
  - 每天重复的折叠成“每天 08:00 ×3”；
  - 时间轴上画一条“现在”线，过去的变淡；
  - 出错或被跳过的才变色。
- **来源**：#1286
- **怎么验**：在 30 条以上的数据里，3 秒内能找到唯一一条出错的。

### 原则 15 · 层次靠表面、边线和间距，不靠两种相近的黑
- **反例**：引用块和自己的消息都是黑底，分不出谁说的（#1194、#1230）。
- **正确做法**：
  - 引用块放在气泡外面，带作者头像、作者色竖条和名字；
  - 自己的气泡用蓝色，白字对比度不低于 4.5:1（WCAG）；
  - 明暗两套主题都要检查。
- **来源**：#1194、#1230、Astra §4
- **怎么验**：脚本算出文字对比度。明暗两套截图对照。

### 原则 16 · 先找 3–5 个好参考，写清借鉴哪一点；借细节，不照搬整体
- **反例**：v3 整体太单调（#1251）。查看细节、查看进度做得太粗糙（#1194）。
- **正确做法**：先列参考，每个写一句借鉴什么，例如：
  - QQ：布局和右键菜单；
  - Claude Desktop：悬浮卡片列表和 todo；
  - Linear：清单和 My Issues；
  - Devin：进度视图；
  - mirasim：设置变更的系统行、“新消息”分隔线等小细节（#1240），但不照搬它的整体质感。
- **来源**：#1194、#1240、#1251
- **怎么验**：设计说明里有参考表，每一行能在原型里指出对应的地方。

### 原则 17 · 用用户听得懂的话
- **反例**：群模板的勾选框里出现 scope、project、team 这类内部词，用户看不懂要选什么（#1278）。
- **正确做法**：
  - 改成“这个团队通用”“只在这个项目用”；
  - 每条一句话说清，旁边写来源；
  - 先说明会带什么、不会带什么，再让用户选。
- **来源**：#1278
- **怎么验**：界面文案里搜不到内部字段名。

## 四、怎么交互

### 原则 18 · 关闭只退一层
- **反例**：群资料 → 成员资料 → 点关闭，全部关掉了（#1194）。
- **正确做法**：
  - ×、返回、Esc 每次都只退一层；
  - 焦点回到触发它的那个控件；
  - 滚动位置不丢。
- **来源**：#1194
- **怎么验**：走查脚本覆盖“群资料 → 成员 → 下一层 → 逐层返回”。

### 原则 19 · 细节要做足：缝隙能拖、草稿不丢、Enter 能发
- **反例**：
  - 面板之间的缝隙不能调宽（#1194）；
  - 没有发送按钮，Enter 的体验有问题（#1230）。
- **正确做法**：
  - 三处分隔线都能拖；
  - 切换会话，草稿不丢；
  - Enter 发送，Shift+Enter 换行；
  - 输入法正在选字时，Enter 不发送。
- **来源**：#1194、#1230、#441
- **怎么验**：脚本量出拖动前后的宽度；在真实用户路径上按 Enter 和 Shift+Enter；切换窗口后检查草稿。

### 原则 20 · 一个状态一屏只有一个主位置；能处理它的入口可以有几个，但要同步
- **反例**：同一个错误在一屏里出现了 5 次（#1248）：会话列表、标题栏、聊天行、托盘、右侧红框。
- **正确做法**：
  - 完整的错误原因和“重试”，只出现在失败的那一步；
  - 其他地方最多留一个红点或数字；
  - 右侧打开详情后，中间不再用红框重复一遍；
  - 从不同入口点“重试”，只算一次（Astra）。
- **来源**：#1244、Argon #1248、Astra §3
- **怎么验**：在出错的那屏截图里，错误全文只出现一次。连点两个入口的“重试”，只多出一次尝试。

## 五、怎么验

### 原则 21 · 只做了入口不算实现
- **反例**：v3 里有些入口点进去是空的；US12 的发邮件、插件市场只做了一个“外部来源”入口（#1235、#1228）。
- **正确做法**：
  - 每个入口都要能走到真实的结果；
  - 做不到的，在覆盖表里标“未覆盖”，不包装成已完成。
- **来源**：#1235、Astra H42
- **怎么验**：覆盖表里每一行都有“入口 → 结果”的截图。只有入口的一律记为未实现。

### 原则 22 · 需求文档逐条对，覆盖表里不能有大片空白
- **反例**：只挑了几条做，文档里很多功能没实现（#1235）。
- **正确做法**：
  - 把 U、US、C-US、AC 逐条拉成清单，每条在原型里落地；
  - 覆盖表写明“编号 → 功能 → 走查链路 → 结果”；
  - 不拿测试条数证明全覆盖（Astra H26）。
- **来源**：#1194、#1235、#1257
- **怎么验**：覆盖表对需求编号做全集比对，没对上的单独列出来。

### 原则 23 · 用自动化走查加截图，走完整条交互链路
- **反例**：靠看静态截图判断体验，没发现关闭会全关（#1194）。
- **正确做法**：照 pstack 的做法，用功能地图加固定脚本，从用户真实入口一步步点下去。每一步截图并断言，明暗主题各跑一遍。
- **来源**：#1194
- **怎么验**：`verify/walk.mjs` 全部通过，截图齐全。

### 原则 24 · 复现用户的路径，不凭代码判断“已修好”
- **反例**：代码里早就有 Enter 的处理函数，但用户实际用起来还是有问题（#1230，Astra H33）。
- **正确做法**：
  - 用户报的问题，先在他的路径上复现，修完再在同一条路径上验一次；
  - 分清三层证据：截图证明视觉，交互证明前端，后端事件证明执行，不能互相替代。
- **来源**：#1230、Astra §6
- **怎么验**：修复记录里有“复现步骤 → 修复前截图 → 修复后截图”。

- **来源**：#1266、#1346
- **怎么验**：每一版原型都能对应到一版已确认的概念卡。

## 七、v4 新增的教训（#1373–#1432）

### 原则 28 · 每个元素先回答三个问题：用户在哪、看的是谁的、点了去哪
- **反例**：“进展”列表里一条“首页打开太慢”，看不出是私聊还是群聊、哪个群（#1395）。用户的话：“没考虑用户理解，本质是偷懒。”
- **正确做法**：聚合视图里每一条都带来源标签（群头像 + 群名，或“与 X 私聊”）。按钮文案写清去向，比如“打开「模型助手群聊」”，不写“打开”。
- **依据**：Nielsen 启发式第 6 条“识别优于回忆”：用户不该靠记忆还原上下文。
- **来源**：#1395
- **怎么验**：走查 F-PROVENANCE。聚合视图里的每张卡都能读出来源。

### 原则 29 · 导航语境要保留：在哪个区域打开的，左侧就停在哪
- **反例**：在“进展”里点开一件事，左侧跳回了聊天。每次都得重新点“进展”，没法总观（#1387）。
- **正确做法**：
  - 左侧一级导航表示“我在哪个区域”，只能由用户自己切换；
  - 打开详情只换中栏和右栏；
  - 只有写明“打开「某群」”的按钮才离开当前区域；
  - 回到原区域时，筛选和滚动位置都还在。
  - 全景画板是遮罩，不是区域（#1618）：打开和关闭都不改左侧导航；关掉再打开，筛选和滚动位置都还在。
- **依据**：Shneiderman“先总览、再缩放过滤、按需看细节”：总览要一直在，细节才有参照。macOS Finder、邮件客户端的侧栏选中态都不会因为打开文件而改变（空间一致性）。
- **来源**：#1387、Argon #1388
- **怎么验**：走查 F-PANO。点节点后 `nav-activity` 仍然选中，切走再回来筛选还在。

### 原则 30 · 动效状态在亮暗两套主题下都要醒目；一种状态只配一种动效
- **反例**：
  - 呼吸灯在暗色里明显，在亮色里几乎看不见（#1387）；
  - 一个 Compute 面板里有 4 个呼吸点：标签页、头像角标、副标题、最后一步，而且“等你”状态用了绿色（#1391）。
- **正确做法**：
  - 去掉呼吸灯；
  - 进行中用转动的环（形状加动效，不只靠颜色）；
  - 等你用橙色实心圆加底色块；
  - 出错用红三角加竖线；
  - 同一视口只在一处画状态；
  - 状态色对背景的对比度不低于 3:1（WCAG 1.4.11 非文本对比）。
- **依据**：Treisman 前注意加工（形状和运动比浅色小点更容易被一眼挑出）；Tufte 数据墨水比（重复的 4 个点不增加信息）；Argon #1248 提出的单一锚点。
- **来源**：#1387、#1391
- **怎么验**：走查 F-CONTRAST 算对比度；F-ONE-ANCHOR 断言分屏里“等你验收”只出现一次、呼吸点为 0。

### 原则 31 · 状态写清“在做什么、回谁、多久”，不要只亮一个灯
- **反例**：头像旁一个闪烁的点，用户不知道它在回哪条、做到哪了（#1412）。
- **正确做法**：照 mirasim 做“正在回复”卡：
  - 卡里带它在回的那几条引用，以及“在想 / 在写 · N 分”；
  - 可以展开看步骤，再往下是“看完整过程 ›”；
  - 消息头像在上、内容往下，天然看得出这条消息是谁的。
- **依据**：Norman 反馈原则（反馈要说清系统在做什么）；Shneiderman 按需看细节。
- **来源**：#1412、#1432、Argon #1433
- **怎么验**：走查 F-REPLYING。

### 原则 32 · 总览和过程分层：一行快照 → 聚合面板 → 完整过程，并且共用聊天模板
- **反例**：进度要么看不到（像 muse 那样全黑盒），要么铺满整屏、必须点 × 才能回去（mirasim 的全景图，#1410）。
- **正确做法**：
  - 第 1 层，聊天流里一行快照；
  - 第 2 层，进展全景画板，用弹出遮罩，点背景或 Esc 关闭（用户 #1618）；
  - 第 3 层，联系人的完整过程，和聊天窗口用同一套模板，只有它一个人在说话，Compute 在里面占一行，点开又是一层。
  - 有两个入口：状态卡上的“看完整过程”，头像菜单里的“看完整过程”。两个入口打开的是同一个视图，从群里进来只看本群。
- **依据**：Shneiderman 的信息检索箴言；Nielsen 一致性原则（同一种内容用同一套模板，用户不用重新学）；渐进披露（Progressive Disclosure）。
- **用户定案（#1618）**：全景画板用弹出遮罩，理由是「进度不是需要时刻打开的」。#1443 主张占中栏加右栏，不采用。弹层丢筛选和位置的顾虑，由「再次打开时恢复筛选和滚动位置」解决（见原则 29）。
- **来源**：#1410、#1427、#1429、#1432、#1443
- **怎么验**：走查 F-PANO、F-REPLYING、F-WORKBENCH 的“完整过程”标签。

### 原则 33 · 职责给别人看，预设给自己看；职责必须被功能读取
- **反例**：职责只是名片上的一行字，不影响任何行为；预设被混写成“预设（Soul）”（#1373）。
- **正确做法**：联系人分五层，每层写清谁写、多久变一次：
  - **职责**：你写，按群设分工；
  - **预设**：你写，偶尔调；
  - **性格**：它自己改，你能回滚；
  - **记忆**：它自己写，你能删、能纠正；
  - **红线**：只有你能改。

  职责要被功能读取：清单认领时按分工推荐人选，Helper 拉群时按分工推荐成员。检验方法：改职责只改变谁来接活，改预设只改变怎么干。
- **来源**：#1370、#1373
- **怎么验**：走查 F-WORKBENCH（职责与预设标签）、F-STORY-A（按分工推荐）、F-CHECKLIST（推荐认领人）。

### 原则 34 · 用户不再挑错之后，自审就是验收的一部分
- **反例**：每一轮都要用户截图指出问题，我们才改。
- **正确做法**：照 poteto/pstack 的做法，用功能地图加固定脚本，每次改完把全部链路跑一遍，亮暗两套主题各截一遍图。自审清单至少包括：
  - 同一状态有没有重复；
  - 对比度（含动效）够不够；
  - 导航语境有没有保留；
  - 返回能不能退一层；
  - 每个元素有没有来源标签；
  - 文档里的功能是否都有入口和内容。

  自审发现的问题写进总账，标“自审发现”。
- **v4 自审的实例**：右键菜单从来没弹出过，原因是 Row 组件不转发事件。用户没指出，是脚本断言失败时发现的。
- **来源**：#1391、#1393
- **怎么验**：`verify/walk.mjs` 亮暗各 24/24。总账里有“自审发现”的条目。

## 八、讨论落档与约束沉淀（#1457–#1480）

### 原则 35 · 讨论出的结论和灵感，当场写进文档并注明来源；只在聊天里说过的不算定案
- **反例**：#1457–#1474 讨论清楚了信任阶梯、两种时间线、内置和插件的划分，#1410–#1443 定了状态卡、完整过程、全景画板，但到 #1475 时，这些都还只在聊天里，需求文档、概念卡没有一处写进去。用户的话：「否则前面讨论的就白讨论了，出现假讨论、假成功。并且可能后续人类一旦忘记这种灵光一闪，后面就永远不会在有灵感了。」
- **正确做法**：
  - 讨论形成结论（用户拍板、认可，或助手之间收敛）后，同一轮工作里写进对应文档：需求写进需求文档的 U 表和 D 节，概念写进概念卡，做法和教训写进本手册；
  - 每条写明来源消息编号，用户原话保留原词；
  - 用户还没拍板的，写进需求文档 8.1 待决，写明各方主张和理由，不替用户定；
  - 写完在聊天里说清写在哪一节。说「已记下」而文档里找不到，等于没记。
- **依据**：组织记忆（Walsh & Ungson）：只存在于个人记忆和对话里的决定，人一换、时间一长就丢；软件工程里的 ADR（架构决策记录）要求决定和理由一起留档，后来的人才能判断它还成不成立。
- **来源**：#1475（群公告原文同此条）
- **怎么验**：随手抽一条已定的讨论结论，能在文档里按来源编号找到；8.1 待决表里没有已经拍板的项，已拍板的里没有用户没认可的项。

### 原则 36 · 本项目开发自己的约束沉淀：教训 → 项目规则 → lint 和门禁（这是开发方法，不是产品功能，#2286）
- **反例**：把「后期只看结果」当成一个开关，以为界面上把过程藏起来，用户就放手了。
- **正确做法**：
  - 每次被用户纠正、验收被退回，先记一条教训（带来源）；
  - 重复出现的教训升级成项目规则；
  - 能机器检查的规则落成 lint、检查脚本或门禁，并记下它来自哪条教训；
  - 这是我们开发这个软件时自己遵守的做法；产品里不内置这套机制（#2286）。
- **依据**：Lee & See（2004）信任校准：信任要和真实能力匹配，依据是可核对的记录；poteto / pstack 前期花大量时间打地基，地基就是这些约束。
- **来源**：#1473、#1474；产品侧 U79、U81 已撤销（#2234、#2286）
- **怎么验**：本仓库门禁里每条规则都能指回一条教训。

## 九、pstack 验收做法（g-group#1524 起）

> 来源：用户 g-group#1524 要求提取 pstack 的验收规则和技巧；分层方案见 g-group#1526。原文是 cursor/plugins 仓库 `pstack/`（poteto-mode 的 playbook、principle-* 技能、docs/guide/06-verify-and-ship.md），下面每条注明出处。只收和我们有关的部分，按我们的工作方式改写。
> 每个 playbook 写成“步骤 → 这一步要交的证据”。证据要放进仓库或收据，能被审查人重跑；只在聊天里说“验过了”不算。

### 原则 37 · 修 bug：先复现，再二分定位，修完在同一处再验
出处：`poteto-mode/playbooks/bug-fix.md`、`principle-fix-root-causes`、`tdd`

| 步骤 | 做法 | 要交的证据 |
|---|---|---|
| 1 复现 | 在用户报问题的同一个入口自己复现（UI 用走查脚本，CLI 跑真实命令）。复现不出来就收紧条件或加日志，直到它出现；只有说清原因、且自己已尽力驱动之后，才请用户帮忙复现 | 复现步骤 + 失败输出或截图，原样贴 |
| 2 定位 | 列出候选原因，每一轮做一个最能缩小范围的检查，用运行时证据排除；看不清状态就加日志读真实值，不猜 | 每个被排除的假设和排除它的那次输出 |
| 3 找根因 | 一直问“为什么”，直到答案是代码里一处错误决定。先判断触发它的状态合不合法：合法就在出错处处理；不该存在就去找是谁产生了它，不在出错处加防护掩盖 | 一句话写清根因在哪个文件哪个决定 |
| 4 先写失败测试 | 有便宜的测试路径就先写回归测试，确认它因为这个 bug 而失败；测试太贵（大量 mock、要真实生产状态）就不硬写，用最接近的可执行检查代替 | 失败测试的提交在修复提交之前（G-RED 会核对） |
| 5 修 | 只改证据支持的最小改动。“也许有用”的顺手防护不上线；被证据否定的假设，它带来的改动要撤回 | diff |
| 6 同处再验 | 回到第 1 步的入口重跑，原来的复现现在通过。“无法判定”或换了入口验的都不算通过，要明说 | 修复前后两次输出原样贴进 PR |

- **同类全修**：找到一个就搜同样的模式，一起修。
- **深挖才找到的事实**：顺手提一个以后一眼能看到它的信号（日志、断言、诊断命令）。

### 原则 38 · 做功能：先定数据形状，切一条能验收的端到端路径
出处：`playbooks/feature.md`、`principle-model-the-domain`、`principle-sequence-verifiable-units`

| 步骤 | 做法 | 要交的证据 |
|---|---|---|
| 1 吃透现状 | 先读懂受影响的子系统怎么工作（本手册原则 1–3 的概念卡也在这一步） | 一段“现在怎么工作”的说明，引用到文件 |
| 2 定数据形状 | 写逻辑前先写出核心类型，选组织方式：状态机胜过散落的布尔值，表或注册表胜过一串分支，类型模型胜过各处重复的形状假设 | 类型定义或状态表，放在 PR 第一个提交 |
| 3 吞吐检查点 | 写四项：哪些步骤必须先做；哪些工作互不相干可并行；哪些状态是共享可写的（先拆开，拆不开才串行）；为什么这样拆最小最安全。不适用的项写“不适用：原因”，不删 | 四项清单写进任务记录或 PR |
| 4 实现 | 按“已知良好 → 一个改动 → 跑检查 → 下一步”推进，每个小单元绿了才做下一个 | 小而有序的提交 |
| 5 真实入口验证 | 在用户会用的入口上验：UI 走完整条链路（原则 23），CLI 跑真实命令，存储读回写入的值 | 走查截图或命令输出；收据里该 AC 指向它 |
| 6 有争议先对抗审 | 设计有分歧时，在交付前找另一个模型专门反驳 | 反驳意见和处理结果 |

### 原则 39 · 性能：先量基线，修完再量，数字要能解释
出处：`playbooks/perf-issue.md`、`principle-explain-the-number`、`benchmark-checklist`

| 步骤 | 做法 | 要交的证据 |
|---|---|---|
| 1 基线 | 在真实入口抓一次基线（trace、profile 或计时脚本），不读源码代替测量 | 基线产物路径和数字 |
| 2 按便宜程度试 | 依次考虑：不做 → 做一次别重复 → 少做 → 晚点做 → 用户看不见时做 → 并发做 → 做得更便宜。前一招达标就停 | 选了哪一招、为什么前面的不行 |
| 3 修完再量 | 同样条件再抓一次 | 修后产物路径和数字 |
| 4 审数字 | 报数前回答：什么限制了这个数；两边是不是都按生产方式跑；有没有报错或错误输出；交替多跑几次，给中位数和范围；用户等待的路径上有没有变化；计时区间里真的做了这件事吗 | 结论只能是“更快 / 更慢 / 无可测差异 / 无法判定”，附运行次数和范围 |

### 原则 40 · 测试测行为，不测实现；不为了变绿弱化断言
出处：`principle-test-behavior-not-implementation`、`tdd` Guardrails、`create-formal-verification-skill`

- **两个想象中的改动**判断一条测试：
  - 把行为改坏（返回错值、漏一个副作用、做两次）。测试还过，它就什么都没证明。常见原因：断言比契约松；期望值是被测代码算出来的；只重述了常量；断言的是测试自己造的数据。
  - 保持外部结果不变、重写内部。测试挂了，说明它钉在实现上，每次重构都要改，还抓不到 bug。
- **正确做法**：从使用者的接口驱动代码，期望值从需求推出来，不从一次运行抄过来；外部服务收到的请求是行为，内部 helper 被调用是实现。
- **不弱化**：不为了迎合错误实现去改测试；除非预期行为真的变了且写明理由，不放宽已有断言、不删测试、不加 skip。
- **没见过它失败的检查不算数**：每条检查至少看到一次它在故意改坏的代码上变红（我们的 R-03、R-05、R-18 都是这条）。
- **怎么验**：G-STUB 的空桩和错值变异、G-TAUTO 的同语反复检查；断言是否被放宽目前靠审查人看 diff（门禁缺口见文末对照表）。

### 原则 41 · 绿不等于安全：独立验证人跑一遍才算
出处：`playbooks/shipping.md`、`docs/guide/06-verify-and-ship.md`

- **只认非作者的结论**：每个 PR 由没写这份代码的助手，按用户的方式把改动跑一遍（父提交对比 PR 头），给出 通过 / 通过附说明 / 不通过。作者只会验自己想做的东西；CI 全绿和机器人审查通过都不是结论，因为它们没像用户那样跑过。
- **审查人**：默认 Codex，Astra 也可（原则 26b，g-group#1531）；作者和审查人必须是不同厂商（R-01）。
- **结论只覆盖它看过的那一版**：变基、追加提交之后要核对内容 hash（我们的 `reviewed_hash`）；变了就要重审，不沿用旧结论。
- **叠起来的 PR 从底往上合**：从最低的未合并 PR 往上，遇到第一个没有通过结论的就停；上面的即使通过也要等。合并后读回 PR 状态确认真的合进了 main，“已排队”“已开自动合并”不算已合并。
- **怎么验**：G-REVIEW、G-PROVENANCE 核对审查人、厂商和 hash；从底往上合由 `scripts/merge.sh` 执行。

### 原则 42 · PR 描述是一分钟简报
出处：`playbooks/opening-a-pr.md`

- 标题用 `type(scope): subject`。
- 正文按顺序写这几节，没内容的删掉：`## Why`（问题和做法，1–3 句，第一句写用户的目标）、`## What changed`（1–3 条）、`## Scope`（必写：覆盖了什么、故意没做什么）、`## Tradeoffs`（只写审查人会问的被否方案）、`## Blast Radius`（影响谁、为什么安全）、`## Verification`（1–3 条，每条是一次真实运行和它的结果）。
- 完整 SHA、逐文件清单、长篇过程放到附带的文件里，不塞正文。
- 优先五个窄 PR，不要一个大 PR；能叠就叠。

### 原则 43 · 同一句话说第二遍，就把它做成结构
出处：`principle-encode-lessons-in-structure`；poteto 访谈（`~/Downloads/x-poteto-2500-prs-transcript.md`：“whenever you see tech debt or bad patterns, your instinct should be, I need to write a lint rule against it”）

- 发现自己第二次写同一条提醒，就把它做成 lint、类型约束、运行时检查或脚本；能让错误在代码库里“根本写不出来”更好。
- 结构化修复做了，文字提醒就删掉，不要两套并存。
- 需要判断、编不进结构的教训，把说明放到显眼处，并附一个失败的例子。
- 和原则 36 的关系：原则 36 是这条阶梯，本条是每次往上爬一级的触发条件。
- **怎么验**：门禁规则表每一行都能指回一条教训来源（`gates.ts` 的 `rule` 字段写了 R 编号）。

### 原则 44 · 先说目标，长任务留决策记录
出处：`poteto-mode` Non-negotiables、`show-me-your-work`、`principle-attack-the-premise`

- 接任务第一句话，用自己的话复述用户的目标、要解决的问题，以及预计最小的改动；证据否定了用户要的改动，就把证据拿出来并停下。
- 能靠跑一下就知道答案的问题（行为、时序、布局、输出），自己做个小原型去看，不问用户；只把产品和偏好上的选择留给用户。
- 两次以上基于同一前提的修复都失败了，先把那个前提写下来并直接检验，再写下一个修复。
- 长时间、自主、多阶段的工作，留一份决策记录（做了什么选择、依据是什么），方便事后审。
- **怎么验**：任务记录第一条是目标复述；连续失败的修复记录里能找到被检验的前提。

## 十、连续投递不丢要求（#1669、#1689）

### 原则 45 · 每条消息都要有交代；完成看承诺账本，不看模型停没停
- **反例**：任务 #866 里，助手在 #1656 承诺"先搭内核骨架，再开 3 个并行切片"。一分钟后 Codex 的转述（#1660）插进正在运行的轮次，助手把"三个并行"换成了 PR 复审和返修，轮次照样记完成，骨架和切片都没做。同一任务早上停下"等 PR #1 合并"，没有唤醒条件，停了约 8 小时，直到用户 #1359 追问。
- **状态**：已定的有：目标（前面的要求不丢，U87）；承诺账本归联系人（#1711）及其直接结果：说出口和接下的事要登记、承诺不按 TTL 静默失效；「完成」必须有产物（AC-16，#2785 最小闭环第 1 项）；联系人层由宿主每轮重拼上下文（D23 第 9 小节，#2667–#2688 定方向）。待审的是具体做法：处置枚举、对账与补 1 次上限、步骤边界合并、唤醒条件格式、五块的具体顺序（需求文档 D23）。以验收文档 AC-40 末列为准。
- **做法（每条标了已定或待审）**：
  - 不在入口把消息分成"任务 / 聊天"。分错了就是静默丢失（用户 #1689；Suchman 1993 对 The Coordinator 的批评）；
  - 〔待审〕推进 `processed_seq` 前，区间内每条消息落一条处置：`done`（附产物链接）、`committed`、`merged→#x`、`superseded→#x`、`noted`。处置可见，用户一句话就能改；
  - 〔已定〕自己说出口的"我会做 X"当场登记进承诺账本，用户交办且接下的事也登记；
  - 〔已定〕没有产物就不算完成，口头说「已更新」「已启动」不算；〔待审〕轮次结束前对账：有消息缺处置，或本轮该推进的承诺没有动作，就不算完成。最多补 1 次，之后如实写"未做：原因"；
  - 〔已定〕承诺只能被完成、撤销、替代或报阻塞了结，不按 TTL 自动消失；〔待审〕等待类承诺必须写唤醒条件和期限；
  - 〔待审〕运行中插进来的消息先给回执，在步骤边界合并；改了原计划要留 `superseded` / `merged`；"停"不等边界（与 AC-40 ④ 同为候选）。
- **依据**：同时满足多条要求的概率随条数近似指数下降（ManyIFEval）；同一任务拆成多轮平均掉 39%（Laban 2025）；长上下文中段信息用得最差（Lost in the Middle）。所以不能指望模型自己记住，要靠宿主对账，结构同 TCP 确认重传、期末结账。
- **来源**：#1669、#1689；Argon #1685、#1695；需求文档 U87、D23；验收文档 AC-40；分析稿 `g-group-requirements/reviews/本源分析-连续投递丢任务-ClaudeCode.md`
- **上下文怎么装（v3.11，需求文档 D06 第 2 小节、D23 第 9 小节）**：联系人每轮不重放整段群聊，由宿主重拼：固定前缀、账本原文、状态笔记、新消息、指针。账本和规矩原文由代码复制，模型只写状态笔记。
- **怎么验**：重放 #866 的插入场景，原承诺要么有 `superseded` 记录，要么被做完，否则轮次不能记完成；跳过一条消息直接推进游标会被拦下；核对实际请求体里没有五块以外的旧消息。

### 原则 47 · 一个联系人做几件事时：用户分得清在回哪件，只有联系人说话，补充不串
- **反例**：同一个 Codex 同时挂着私聊的「排查 Meta Raycast 快捷键冲突」和群里的「PR #3 返修后跨厂商复审」，两张卡片长得一样，进度各刷各的。用户分不清自己在回哪件（#1728、#1731）。
- **已定（照做）**：
  - 用户分得清在回哪件（U88，目标）；
  - Compute 不在群里直接发言，只有联系人对外说话（U70、U84；AC-40 ⑧ 当前必过）；
  - 补充不串到另一件任务（U13；AC-40 ⑨）。
- **候选做法（待审，需求文档 D23.7，用户未批准；实现前先问用户，不按本条强推）**：
  - 联系人接下任务时起一个短名（如「快捷键」「PR#3 审查」），同名下不重名，用户可改；
  - 联系人只转三类：要你决定的问题、结果、卡住；普通进度留在任务上；
  - 联系人的每条汇报，每件事一行，以短名开头；几件事同时有结果时，合成一条消息；
  - 绑定顺序：引用了带标签的消息 → 话里出现短名 → 名下只有一件同类在途任务 → 联系人自己判断，并在原消息下标「→ 短名」，可一句话改绑。不弹「补充还是另开」卡片；
  - 一件事一个 Compute，补充只送给绑定的那一个；联系人只带账本和摘要。
- **依据**：dsh-superagent（main Session 当 Router、每件一个 Ticket、只在有人必须行动时说话）、Muse（一条主对话，后台只报有价值的）、GrokBot（幕后一行灰字加主控结论）三家都是「对用户一个声音，幕后多件事」；同时要满足的要求越多，全部做到越难（ManyIFEval），所以上下文要按任务隔离。
- **来源**：#1728、#1731；Argon #1709；需求文档 U84、U88、D23.7；验收文档 AC-40 ⑦–⑨
- **怎么验**：重放 #1728，引用审查汇报说的话只进审查那件，不串到快捷键；群里看不到 Compute 直接发的进度。（「未引用时原消息下有 → 短名」属候选方案，批准后再加）

## 十一、模型调用成本（#1493）

### 原则 46 · 缓存只认逐字相同的前缀：稳定的放前面，会变的放最后
- **反例**：mirasim 群聊用量页命中率只有 38.8%，鸿运线 16%。助手初判是「system 前部塞了滑动窗口」，实测后发现客户端前缀其实稳定，问题出在中转只缓存住固定头部（命中数恒为 42643）；另一条 kiro 线报 80%，但每次都恰好是输入的 4 倍，是拆账数字。两个教训：先拿请求体和用量日志实测再下结论；报告出来的命中率本身也要验真。
- **正确做法**：
  - 前缀顺序固定：系统提示词 → 工具定义 → 人设与群公告 → 规矩原文；之后才是每轮重拼的账本、状态笔记、新消息（需求文档 D06 第 2 小节，v3.11）；
  - 会变的东西不进前缀；规矩变了前缀就跟着变，不为缓存沿用旧规矩；
  - `cache_control` 最多 4 个，放在稳定段末尾，最后一个跟着最新消息走；
  - 一个联系人在一个群里只用一个常驻会话，并固定在一条线路上；
  - 每次调用记 `input / cache_read / cache_write / 线路`，按线路 × 联系人 × 群出命中率，先过可信度检查再报警。
- **依据**：Anthropic 与 OpenAI 的提示缓存都是前缀匹配；本机 magpie 实测：鸿运线按「上一轮完整前缀被缓存」算理论上限 92.1%，实际 16.4%。
- **来源**：#1493、#1494；需求文档 U85、D22；验收文档 AC-39；证据 `g-group-requirements/evidence/cache-20261105/`
- **怎么验**：相邻两次请求体前缀哈希一致；system 段扫不到会变内容；喂入 4:1 拆账数据会被标「拆账口径」。

## 十二、空间、入口与视觉验收（#1560–#1651）

### 原则 48 · 决策先作为一条消息发出去，再考虑卡片
- **反例**：v4 把要你拍板的事做成 Ask 卡（A2UI），放在输入框上方的托盘里。验收、选方案、同意提议，全都塞进卡片，用户问：“什么都 A2UI，还要对话消息和 @、引用干嘛？”（#1560）
- **正确做法**：
  - 提问的助手在消息下方挂几颗快捷选项。用户点一下，就以用户的名义发一条引用原问题的回复，群里人人看得见，这条回复本身也成了后续的上下文。
  - 选项最后放一颗带笔图标的「自己回答」。点了以后输入框引用原问题并 @ 提问者，光标进入输入框（#1607）。
  - 选项排成一行。未选中的选项用实线描边和正文颜色，不能灰到看着像不能点（#1651）。
- **依据**：Clark《Using Language》的共同基础：决定要落进双方共有的记录里才算数。Cooper《About Face》：给出选项，但不剥夺用户自己表达的权利。
- **来源**：#1560、#1607、#1651
- **怎么验**：点任一选项，群里多出一条用户发的引用回复；F-VISUAL 断言每组选项只占一行。

### 原则 49 · 同一件事只设一个入口，其余位置不重复
- **反例**：进度同时出现在三处：输入框上方的“N 件事在等你”、标题栏的“在跑”、消息流里的 Compute 行（#1607）。头像菜单有 11 项，每项还带一行说明（#1651）。工作台顶部的“五层说明条”和下面各分区的标题说的是同一件事（#1607 附图）。
- **正确做法**：
  - 进度只保留消息流里的 Compute 行；跨群的总览放在「进展」遮罩里（#1618）。
  - 点头像出资料卡，卡上放 4 个动作（@它、私聊、看过程、资料），其余收进「更多」。
  - 说明文字并进它所说明的那个分区的标题行，不另起一条。
- **依据**：Tufte《The Visual Display of Quantitative Information》的数据墨水比：重复出现的同一信息就是多余的墨水。Hick 定律：选项越多，决定越慢。Krug《Don't Make Me Think》：先删掉噪音。
- **来源**：#1560、#1607、#1651
- **怎么验**：F-VISUAL 断言资料卡不超过 5 项；全局搜不到输入框上方的等待提示和标题栏的进行中标记。

### 原则 50 · 空间按使用频率分配：低频的东西不常驻，按需在分栏里打开
- **反例**：v4 的群右栏常驻 264px，内容只到 452px，视口 900px 高，下面一半是空的。群只有 5 个成员，不值得占一整栏（#1593、#1651）。聊天顶部叠了三条：标题 52 + 清单 32 + 置顶 45 = 129px（#1651）。
- **正确做法**：
  - 默认不显示右栏。成员头像叠放在标题栏，点开后在右侧分栏显示；群资料和联系人详情共用这一个分栏位置。
  - 分栏默认 400px，可以拖动调宽；聊天列最窄 560px。分栏里只有一层页签。
  - 聊天顶部只留一行：公告和置顶合并成一条轮换（1/N 切换，喇叭图标是群公告、图钉图标是置顶消息），右边放清单、定时、插件的小胶囊。顶部总共 92px，占视口 10.2%。
- **依据**：Fitts 定律加上 Miller 的有限注意：常驻区域只留给高频、和当前任务相关的东西。格式塔的共同区域原理（Palmer 1992）：一行之内是同一组，读起来比三条叠放更省力。
- **来源**：#1593、#1651
- **怎么验**：F-VISUAL 断言顶部占用不超过视口 11%、聊天列不小于 560px；F-SIDE 断言默认没有常驻右栏。

### 原则 51 · 查看详情用分栏，不用遮挡聊天的弹层；只有不需要一直开着的总览才用遮罩
- **反例**：点头像看联系人详情时弹出浮层，盖住了聊天（#1620）。
- **正确做法**：
  - 联系人详情、群资料、Compute 详情都在右侧分栏打开，和聊天并排。
  - 进展全景例外，用弹出遮罩，因为“进度不是需要时刻打开的”（#1618）：点背景或按 Esc 关闭，关了再开，筛选和滚动位置还在；点「打开会话」先关遮罩再跳过去。
- **依据**：Raskin《The Humane Interface》：不打断用户正在看的东西。Shneiderman 的“先总览，再按需看细节”。
- **来源**：#1618、#1620
- **怎么验**：F-REPLYING、F-CARD 断言没有 float 浮层；F-PANO 断言遮罩开关都不改左侧导航。

### 原则 52 · 功能走查全过不等于好看：每屏和参考产品并排对照，并把视觉指标写进走查
- **反例**：29 条走查全过（29/29），用户还是说“太丑”“像学生产品”（#1593、#1651）。原因是那 29 条全是 DOM 功能断言，没有一条检查视觉。
- **正确做法**：
  - 照 pstack 的 `poteto-mode/playbooks/visual-parity.md`：每屏在同样的视口下，和 QQ、mirasim 的参考截图并排对照，逐处说明借了什么、哪里不同。
  - 能量化的视觉指标写进走查（F-VISUAL）：顶部占用、选项是否折行、菜单项数、聊天列最小宽度、分栏是否留空白。
  - 只有用户说好看才算好看。模型自评好看不作数。
- **依据**：pstack 的 principle-prove-it-works 和 visual-parity；Nielsen 的启发式评估要靠真实画面，不靠功能清单。
- **来源**：#1593、#1651
- **怎么验**：交付时附并排对照图；F-VISUAL 亮色、暗色都通过。

## 十三、验收就是一句回复（#1744 #1754）

### 原则 53 · 真人怎么交活，agent 就怎么交活：不给验收造专门的组件

- **反例**：Codex 做完后，聊天里插了一块暖橙色的「首页打开太慢 · 等你验收 [去验收]」，汇报消息下面还挂着「验收通过 / 还要改 / 先看改动」三颗气泡。用户说这既鸡肋又突兀（#1744）。真人交活从来不带这种按钮，只会发一句「@你 改完了，可以验收了」（#1754）。
- **原因**：这是把后台的状态机（待验收）直接画成了界面组件。它和 @、回复、引用三件事重复，也在聊天里多造了一个状态锚点。
- **正确做法**：
  - Compute 过程在聊天里只留一行折叠的灰字，点开看过程。
  - 交付就是一条普通消息：正文里 @你，说清结果和证据。
  - 你回复这条汇报，说「通过」「没问题」之类，清单那一行就自己推进到「已完成」。想改就直接回复写要改什么。
  - 快捷气泡只给真正的选择题（几个选项加 ✏️ 自己回答）和规则变更提议。交付不挂气泡。
- **依据**：
  - Argon 在 #1747 的结论：减法原则，现有对话原语能解决的不另造 UI。
  - 社会临场感（Short, Williams & Christie 1976）：群聊的价值在于共享上下文，决定本身就是对话的一部分。
- **来源**：#1744、#1747、#1754
- **怎么验**：走查 F-NO-ACCEPT 断言聊天里没有「等你验收 / 去验收」，汇报消息下没有气泡；回复「没问题，通过」后，清单 t2 变成已完成。

### 原则 54 · ✏️ 自己回答 = 引用 + @ + 聚焦，一样都不能少

- **做法**：点 ✏️ 自己回答，输入框同时完成三件事：挂上对这条消息的引用、在开头填好 `@作者 `、把光标放进输入框。用户直接打字回车就能发。
- **来源**：#1607、#1747、#1754
- **怎么验**：走查 F-OWN 断言引用 1 条、输入框以 `@Argon ` 开头、焦点在输入框；打字回车后消息带着引用发出。

### 原则 55 · 消息优先，状态灰字挂在消息最下面

- **反例**：Codex 的「首页打开太慢 · 首屏 3.1→0.9 秒」灰字单独占一行，夹在「我分一个 Compute 去查」和汇报消息中间（#1790）。
- **做法**：
  - 一个 Compute 有了汇报消息，过程灰字就挂到那条消息下面：顺序是气泡、表情、灰字。
  - 还没汇报的 Compute（在跑、出错）才单独占一行，因为那时它就是最新的事。
- **来源**：#1790
- **怎么验**：F-NO-ACCEPT 断言 `trail-g6` 在汇报气泡下方，聊天里没有单独的 g5c 一行。

### 原则 56 · 合并还是拆开，看是不是同一个回合

- **反例**：Argon 的提问、它下面的选项、紧接着的另一个提问，三样贴在一个头像下，间距只有几像素（#1794）。
- **规则**：
  - 合并：同一个人、同一件事、5 分钟内连着说。这些消息挂在一个头像下，间距 2px，像一口气说完的几句话。
  - 拆开：下面任一成立就拆，重新露出头像、名字和时间，和上一条隔 16px。
    1. 这条消息带引用，也就是在回应别的事。
    2. 上一条挂着要你回答的选项，或挂着做完的过程。那是一个回合的结尾，后面的话是新的一件事。
    3. 和上一条隔了 5 分钟以上。
- **依据**：
  - 格式塔的接近律：离得近就被看成一组，所以间距本身就在表达"是不是一件事"。
  - Slack 和 Telegram 都按时间窗合并连续消息。
  - 话轮（turn-taking，Sacks, Schegloff & Jefferson 1974）：一个提问等对方回答，就是一个话轮的结束。
- **来源**：#1794、#1796
- **怎么验**：F-VISUAL 断言 quick-g12 和下一条消息间距 ≥ 12px，下一条 g13p 重新露出头像。

### 原则 57 · 同一高度的空位要用起来

- **反例**：过程灰字占一行、表情标签占一行，两行左右都空了一大半（#1839）。
- **做法**：一行能放下的不拆成两行。灰字靠左，表情靠右下角。#2862 起表情不再表示已读，已读看气泡旁的回执按钮（原则 66），同样不另占一行。
- **来源**：#1593（空间是珍惜资源）、#1839
- **怎么验**：F-NO-ACCEPT 断言表情和灰字中线相差 < 6px，表情右边贴着气泡右边。

## 十四、定时与实测验收（#1844–#1858）

### 原则 58 · 一个能力要做完整个生命周期，不是只做展示

- **反例**：定时有三处列表（群、工作台、进展），却不能新建、修改、删除，没有运行记录，到点的消息也跳不回它的定时（#1850）。“只有入口、点进去是空的”的变体：能看，但不能用。
- **定时的本质**（Argon #1858）：联系人的自主唤醒，由五样东西组成：谁、归属会话、何时醒、醒来做什么、什么时候才开口。每次醒来是一次运行，有三种结局：
  - 有话要说：发一条消息，底部挂灰字「来自定时」；
  - 无事：静默，不发消息，只在运行记录里留一行；
  - 出错：原地标红，可以重试。
- **生命周期检查单**：创建（在对话里说一句，或在列表里就地新建）→ 查看（三个范围看同一份数据）→ 修改、暂停、删除 → 立即试跑 → 运行记录 → 和消息互相跳转 → 改动留痕（一行灰字，不让助手发气泡）。
- **来源**：#1286、#1850、#1858
- **怎么验**：F-CRON-CHAT、F-CRON-EDIT、F-CRON-PANEL。

### 原则 59 · 走查要分两种：冻结的看画面，不冻结的测交互逻辑

- **反例**：33 条走查全部带 `freeze=1`，“做完 → 汇报 → 清单推进”这条会动的链路一次都没跑过（遗漏核查 B 组）。另有两处断言带 `|| true` 兜底，永远不会失败。
- **做法**：
  - 冻结的走查负责画面和截图基线：`verify/shotdiff.py` 逐像素比对，有变化时人看三联图再收为新基线。
  - 不冻结的走查负责真实时序：F-LIVE 测交付链路，F-PERF 测空闲 CPU 和内存。
  - 断言不许兜底。写不出真条件，就说明这项没有验证。
- **依据**：pstack 的自动化验收和交互逻辑实测验收（#1387、#1844）。
- **来源**：#1387、#1560、#1844

## 十五、消息投递与引用链（#2079–#2088）

### 原则 60 · 投递带引用的消息，要把引用链连上，并标明上面还有没有

- **反例**：用户在 `#2071` 回 `#2067`，`#2067` 又回 `#2064`，`#2064` 又回 `#2063`。投递时只附了「回复 #2067」一级，用户说的「用图谱存用不着」其实在 `#2063`。那次能接上，只是因为 `#2063` 恰好还在同一会话里（#2081）。
- **做法**：
  - 宿主在新消息后面附 `quote_chain`：按层往上带前 3 级（#2115 确认），同一条只出现一次；会话里已有的只标编号（`in_context`），不重贴。
  - 每一级都写 `has_more_above`，整条链写 `depth_total`；没带全时给 `truncated` 和 `next_seqs[]`。
  - 更深的由联系人调 `read_quote_parent(seq)`，一次只读一级。
  - 只追加在尾部，不改前缀（原则 46）。遇到已删、撤回或无权读的一级就停，不越过它往上走。
  - 字段表见需求文档 `D24` 第 3 节。
- **依据**：人看不懂上一条会再点上上一条（#2079）；模型通常察觉不到自己缺了前文，所以前几级由宿主默认带，深的给信号和工具。这是投递机制，不是记忆设计（#2084）。
- **来源**：#2079、#2081、#2084、#2088、#2115
- **怎么验**：验收文档 `AC-41`，重放 `#2071` 往上 14 级这条链（到 `#1979`）。

### 原则 61 · 动手前先判断它是不是软件该做的事

- **规则**：每补一项功能，先问一句：它解决的是软件能核对、能执行的事实，还是人在某个阶段的主观判断？主观判断（信不信它、放不放手、喜不喜欢）留给人，软件不替人做、不替人记档位。判断不了的，先列出来问用户，不直接做。
- **反例**：放手档位（看过程 / 看里程碑 / 只看结果）和据通过率建议改档。用户 #2234：「这种是否放手只是我们主观对阶段对信任在不同时期的信任问题，这根本不属于软件层面的。」又如把 pstack 的「教训 → 规则 → 门禁」做成软件内置机制，用户 #2286：「如果你说的沉淀机制是pstack的这种方法论的话那么这是属于上层的软约束的，软件不该做」。
- **来源**：#2234、#2239、#2286；逐条分类见需求文档 §2.0

## 十六、记忆的读与写（#2071、#2375）

### 原则 62 · 记忆要做好的是读和写，不是规模；记下就生效

- **反例**：#2063 说「几百条用不上图谱」，按规模定结构。用户 #2071：「如果长期用很久，那么规模肯定会很大，所以现在其实考虑的是如何让读和写变得更好，而不是考虑规模问题」。又如给每条新经验加回放验证或门禁才生效，用户 #2375：「这种不需要，很麻烦」。
- **做法**：
  - md 是真源，关系和锚点是 frontmatter 里的一等数据；索引从 md 派生，随时可重建。
  - 写：当前会话顺手写；先定锚点，再在邻域里判关系。复述挂佐证，改变出新版本并替代旧条目，冲突且都来自用户原话就问用户。写完立即生效。
  - 读：按当前动作的锚点和状态硬筛，再排序，在相关度断崖处截断，没展开的给 id 和标题；不整份读入全量索引。
  - 前缀不设 token 预算，只看准入：每轮都适用的才进前缀；大小只观测，超水位提示复查，不截断（#2391）。会话中途的变化按版本号只追加一次。
  - 用的时候顺手记效果，反复出错的降级，不删除。
  - 不另配模型（#2362）。
- **来源**：#2071、#2375、#2362、#2064、#2067、#2391、#2393；需求文档 `U90`、`D25`
- **怎么验**：验收文档 `AC-42`。

## 十七、进度的反查与维护（#2422、#2430、#2734）

### 原则 63 · 进度由软件从 harness 核对出来，联系人查的和画板显示的是同一份

- **反例**：父会话显示「运行中 · 已跑 4 分」，下面的后台任务早已因宿主进程退出成了孤儿（`#2430` 截图红框）。又如会话只存 `completed / incomplete` 两种结局，人停的和断流的分不开，联系人没法判断该不该重跑。又如 `cyber_policy` 拒审后在原会话「继续」，必然再失败（`#1697`）。
- **做法**：
  - 一张只追加的运行台账，覆盖联系人轮次、Compute 会话、轮次、后台任务、子代理，带父子关系和来源群 / 私聊。
  - harness 回调写状态，存活核对兜底：进程不在就标 `orphaned`；失败必带原因分类和原始错误。
  - 查询工具按私聊 / 群划分可见范围；全景画板和工具读同一张台账。
  - 重跑只针对失败、中断、孤儿；人停的不自动重跑，平台拒绝的换新会话，不知道副作用的先说明。
  - 自己名下 Compute 失败的任务可自行重跑，最多 2 次；别人名下的任务不自动重跑，要明确发起并在群里留记录（#2628）。
- **来源**：#2422、#2430、#2628；需求文档 `U91`、`D26`
- **怎么验**：验收文档 `AC-43`（Control CLI 走查画板并截图）。

### 原则 64 · 卡住的轮次由宿主判失败，失败要说清是哪一类

- **反例**：上游收下请求后一直不回，harness 不报错也不退出，画板一直显示「运行中」，长时间自治时没人发现（`#2734`）。又如 harness 每隔几秒报一次「正在重试」，宿主把它当成进展，一直重试、反复上传整段对话烧额度。又如「Prompt is too long · automatic compaction failed」被记成笼统的失败，用户不知道该换上游还是开新会话。
- **做法**：
  - 分清两层：harness（如 Claude Code）只管单次请求的超时与重试，整轮无进展判失败由宿主做（`#2735`、`#2745`）。
  - 每个运行中的轮次记最后一次进展时间；只有真实事件算进展，重试公告、心跳、进程存活都不算；等人回答、工具在跑、首字节窗口内不计时。
  - 到阈值按停止流程收掉，写 `failed` + 原因类别 + 原文 + 用时；不会自愈的错误（鉴权、额度、上下文超长）不等阈值。
  - 原因类别由代码按规则表归类，认不出记 `unknown` 留原文；能否自动重试另存一个字段，不和原因类别混用。
  - 画板显示「失败 · 原因 · 用时 · 打开会话」，用户据此自己换上游；软件不替用户换。
  - 阈值已定（#2827）：一轮 15 分钟无进展判失败，首字节等 120 秒；可按联系人或按上游单独设，未设的用默认值。代码里仍是参数，验收夹具用短阈值。
- **来源**：#2734、#2735、#2745、#2747、#2827；需求文档 `U92`、`D26` 第 8 节
- **怎么验**：验收文档 `AC-43` ⑦–⑨、坏实现 ⑩–⑯（夹具上游不回应、只报重试不出输出、长工具不误判，Control CLI 截画板）。

## 十八、已读回执（#2862）

### 原则 66 · 已读由宿主按位置判定，不用表情标记

- **反例**：
  - 原方案让每个模型收到消息后在消息下点一个表情来表示已读（#30、#732）。每人每条要多调一次模型，群里被表情刷满；模型点了表情也不能证明它真读过（#734）。
  - mirasim 群聊的已读名单只算人，不算助手。照搬过来，用户就看不出联系人有没有读到，而这正是要解决的问题（#732）。
- **做法**：
  - 照 mirasim 的已读回执（#2862）：自己发的消息旁一个小按钮，全读了是对勾，没读全是按比例填充的小饼；点开「已读 N / 未读 N」，列出每个人和几点读到，被 `@` 的人带 `@` 标排在前面；正文里 `@名字` 后面一个小点，提示他读没读。
  - 每个成员在每个房间、每个话题各有一个已读位置，位置 ≥ 消息 seq 就是已读。位置由宿主推进，模型的文字、表情、工具调用都改不了它。
  - 群里的联系人全部进名单。
  - 消息被联系人接走就算已读（#3035）：宿主把它交进联系人的这一轮（或插话被接进当前这一轮）的那一刻。还在排队、联系人还在跑上一轮，都不算（U35）。
  - 已读位置只用于显示。消息处理没处理、重跑从哪开始，只看 `processed_seq`；接走后这一轮失败，回执不退回未读，消息照样会被重跑。
  - 已读也不等于办完：做完没有看承诺账本和落点标签，不看回执。
  - 表情保留为普通回应（#3035），联系人和用户都能点，只是不表示已读。
- **来源**：#30、#732、#734、#765、#2862、#2891、#3035；需求文档 `U35`、`D09.3`、`F04`
- **怎么验**：验收文档 `AC-46`：群聊名单漏掉联系人、还在排队就标已读、点表情或说「收到」就记已读、拿已读冒充已落实、拿已读位置代替 `processed_seq` 判定已处理，这几种坏实现都要红；Control CLI 截回执按钮、浮层和 `@` 小点，亮暗各一。

## 十九、磁盘：谁建谁清，做完一步就清（#2900、#2935）

### 原则 67 · 任务做完一步，就清掉自己这一步建的、之后不再用的东西；测试代码自己建的临时目录自己删

- **反例**：
  - 11-05 到 11-06 两天，数据卷可用空间降到约 40G（#2900）。实测 11-03 以来新建、仍留在盘上的文件约 37G，其中 g-group 开发产生的约 14G：`/tmp/g-group-*` 审查克隆约 4.1G、`$TMPDIR/codex-g-group-*` 审查克隆约 3.2G、`deliverables/g-group-pr4-round*` 等审查证据目录约 5.4G、`/tmp/gg-*` 原型冻结链约 1G。每轮审查都整仓克隆一份、再装一份约 110M 的 `node_modules`，十几轮下来就是几个 G，而证据本身只有几 MB。
  - 测试代码建临时目录不删：门禁 `scripts/gates/lib.ts` 的 `gitEnv()` 每个进程建一个 `gate-home-*`，`adapter-cc-compute` 的 `start()` 每次建 `g-group-cc-*`，`adapter.test.ts` 的 `fake()` 建 `fake-cc-*` 后只回收进程、不删目录。两天在 `$TMPDIR` 留下 `gate-home-*` 约 7 万个、`fake-cc-*` 3.8 万个、`g-group-cc-*` 3.4 万个。
  - 走查脚本 `verify/walk.mjs` 用 `/Applications/Google Chrome.app` 真 Chrome，进程被杀时 Chrome 来不及删自己的 `code_sign_clone`，`$TMPDIR/../X/com.google.Chrome.code_sign_clone` 两天堆了 530 份。这些是 APFS 克隆，同版本共享数据块，实际占用远小于 `du` 显示的 1.1T，但每换一个 Chrome 版本就会多压住一份完整副本。
  - 只发群公告，在跑的任务看不到；用户要求把规则通知到所有在跑的任务（#2935）。
- **做法**：
  - **谁清**：谁建谁清。任务（含它派出的子代理、审查会话）只清自己建的目录和文件；别的任务、别的会话的东西不动。属主拿不准就当别人的，列出来交给用户定。
  - **什么时候清**：每做完一步就清这一步的，不等整件事结束。一步指一轮审查出结论、一轮返修推送、一次收据贴出、一个 PR 合并。任务结束时再查一遍，自己名下不应留下临时目录。
  - **清什么**：`/tmp`、`$TMPDIR` 下自建的临时克隆、构建产物、冻结副本、`node_modules`、截图、日志、一次性脚本和一次性测试代码；`deliverables` 下审查证据目录里克隆仓库带的 `node_modules`（可重装，不是证据）；合并或作废后的 worktree。
  - **不能清**：还在用的（正在跑的验收链、在审 PR 的工作区、别的会话正在读写的目录）；报告、收据、PR 正文引用的证据文件；仓库里提交的测试；截图回归基线。要留的证据先挪进 `deliverables/<任务>/` 再删临时目录，报告里改成新路径。
  - **测试代码**：`mkdtemp` 建的目录必须在 `finally` 或进程退出钩子里删除；长期复用的（如门禁的隔离 HOME）进程结束时删。自动化走查优先用 Playwright 自带的 Chromium 或 Chrome for Testing，不用 `/Applications` 里的真 Chrome；必须用真 Chrome 时以 `browser.close()` 正常退出，不靠杀进程收尾。
  - **审查克隆**：同一 PR 的各轮审查尽量复用一个克隆，`git fetch` 到新 HEAD 再审，不每轮重新克隆、重装依赖。
  - **报量**：清完在自己的线程里用一句话说清了多少（以 `df` 的可用空间变化为准；APFS 克隆用 `du` 会多算）。拿不准的列出路径、大小、为什么拿不准。
  - **通知**：这条规则写进每份新开任务、子代理、审查会话的 brief，不只靠置顶公告（#2950）。
- **来源**：#2900、#2935、#2950；群公告（置顶）
- **怎么验**：任务结束时 `ls -d /tmp/<本任务前缀>* $TMPDIR/<本任务前缀>*` 为空或只剩已说明要留的；门禁和适配器测试跑一遍前后数 `$TMPDIR` 下 `gate-home-*`、`fake-cc-*`、`g-group-cc-*` 的个数，不应增加；brief 模板里能搜到「清盘」。

## 二十一、Automation 模型选择：不得使用排队模型（#3369、#3373）

### 原则 69 · Automation 必须使用不排队的模型，不得使用导致排队的共享额度模型

- **反例**：11-07 巡检 automation「g-group 前后端落地巡检 v4」使用 DeepSeek v4.1-flash 模型,用户 #52 截图显示该模型在排队,导致其他 automation 也排队等待。
- **做法**：
  - 所有 automation(schedule_task)必须使用**不排队的模型**,例如 `[kiro企业优化]claude-opus-5-5`。
  - 禁止使用会导致排队的共享额度模型(如 DeepSeek v4.1-flash 的部分 profile)。
  - 模型选择原则:优先使用用户账号下带 `ai-iisbo-2/` 或 `ai-iisbo/` 前缀的模型,通过 `~/.mirasim/setting.json` 的 profiles 查看可用模型及其 providerId 与 modelId。
  - 创建或修改 automation 时,在 model 字段指定不排队的 profile ID(格式 `profile:<id>`),避免使用会排队的 profile。
  - 定期检查 automation 列表(`watchSchedules` atom 或 `~/.mirasim/assistants/.mirasim/schedules.json`),确认所有 automation 都使用不排队模型。
- **来源**：#52(用户发现 DeepSeek 排队)、#3369(通知与规则)、#3373(更正说明)
- **怎么验**：运行 `watchSchedules` atom 或检查 schedules.json,核对每个 automation 的 model 字段对应的 profile,确认其 modelId 是 `ai-iisbo-2/` 或 `ai-iisbo/` 前缀的不排队模型;用户截图或监控面板不应出现 automation 因模型排队而延迟执行。

## 二十二、模型改了下一轮就跟上（#3612、#3619、#3637、#3645）

### 原则 70 · 每一轮都把生效模型交给常驻 harness，在会话内换模型 id，不重启

- **反例**：
  - mirasim 0.0.774 改了助手模型后，在任务话题里重试仍用旧模型，用户只能手动切（#3612）。源码里任务话题续用会话时不传助手的新模型，退回会话记住的模型（需求文档 `F05`）。
  - 助手在 #3618、#3620 两次答「检测到模型变化就关旧 harness、起新 harness」，被用户 #3619 否定：「不是可以直接切换模型id吗？」实测三个 harness 都能在会话内直接换。
- **做法**：
  - harness 常驻：同一个进程跨轮存活，从 stdin 接新输入。有没有 `-p` 不是判据，Claude Code 用 `-p --input-format stream-json` 也是常驻的。
  - 每一轮开始前现场解析这一轮的 `{model, effort}`，交给适配器。不复用会话启动时的模型，重试、任务话题、插话恢复都走同一个解析。
  - 适配器在轮边界比对进程当前实际模型，不同就在会话内换：Claude Code 发 `set_model` 控制请求，Codex 在 `turn/start` 带 `model`，pi 发 RPC `set_model`。会话 id、进程、后台任务、子代理都不动。
  - 一轮进行中改了模型，这一轮按原模型跑完。Claude Code 在一轮中途收到 `set_model` 会立刻换，所以只在 `result` 之后、下一条输入之前发。
  - 切换被拒或超时：这一轮不发，告诉用户怎么修，不退回旧模型继续跑。
  - 只有适配器声明不支持会话内换模型时，才重启并用同一会话 id 接回（Claude Code `--resume`，Codex `thread/resume`）。
- **来源**：#3612、#3617、#3619、#3637、#3640、#3645；需求文档 `U93`、`D27`、`F05`；实测 `g-group-requirements/evidence/model-hotswap-20261107/`
- **怎么验**：验收文档 `AC-51`：只在启动时定模型、重试不带模型、检测到变化就重启、一轮中途发 `set_model`、切换失败照常发出，这几种坏实现都要红；以网关逐请求记录的实际模型为准，不以配置值为准。
